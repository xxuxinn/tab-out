Tab Out · feature assessment · 26 Sep 2026

Which page content should topic grouping run on?

Tab Out groups open tabs by domain. You want a second view that groups them by what each page is about. This page says which content to use, why, and how to turn it into topics without leaving the browser.

Verdict
Use the cleaned tab title plus the words in the URL path. Nothing deeper.

Chrome already gives the extension both, for every tab, in one call, in about a millisecond. The extension already cleans titles. Every richer signal costs a new permission, a per-tab crawl, and fails on sleeping tabs.

Findings

Why title and path, and not the page body

F1 Title and URL are free. Everything else is expensive.

The tabs permission you already hold returns the title of every open tab with no page loading. Chrome keeps the title even for discarded (sleeping) tabs. Reading a meta description, Open Graph tag, page body or video description needs the scripting permission plus <all_urls> host access, a script injected into each tab one at a time, and it fails on sleeping tabs, PDF viewers and internal pages. That turns a 1 ms read into a multi-second crawl and makes Chrome warn "read and change all your data on all websites".

F2 Titles are already topic-rich on the sites that matter.

SiteWhat the tab title holdsWhat the path adds
YouTubeThe video title ("How Transformers Work - YouTube")/watch, so treat it as a video
Google Docs / NotionThe document titleNothing useful (opaque IDs)
GmailThe email subject#inbox/ vs #sent/
GitHub"owner/repo: description"/owner/repo/issues/12, repo name and section
RedditThe post title/r/subreddit/, a ready-made topic label
arXiv, Substack, newsThe article titleSection slugs like /technology/
X"user on X: tweet text", already normalised by stripTitleNoiseUsername

Weak spots: login-walled tabs show "Sign in", some web apps show a bare product name, and titles come in whatever language the page uses. Those tabs fall through to the domain group, which is fine.

F3 Chrome's own tab groups are a free, strong signal.

Each tab object already carries groupId. If the user hand-grouped tabs in Chrome, that is the best topic label you can get. Reading the group's name needs only the small tabGroups permission. Treat a user-made group as a fixed topic before running any automatic grouping.

Options

Turning the text into topics

Ordered from cheapest to smartest. Tab Out promises "100% local, no data sent anywhere" in both README and AGENTS.md, so that column decides more than quality does.

OptionHow it worksCostQuality100% local
O1Keyword rules LOCAL_TOPIC_RULES in config.local.js: a topic name plus keywords matched against title and path. Same pattern as the existing LOCAL_CUSTOM_GROUPS. Zero. Runs in the grouping loop. Only knows topics you wrote down. Yes
O2Local text clustering Tokenise title and path, weight words by TF-IDF (rare words count more), cluster tabs whose word sets overlap, label each cluster by its top 2 or 3 words. Under 10 ms for 100 tabs. No library. Finds new topics. Labels read like "react hooks state". Yes
O3Local embedding model Load a small sentence model in the browser (transformers.js, about 23 MB once), embed each title, cluster by cosine similarity. One-time download, then about 100 ms. Groups "MiniLM tutorial" with "sentence embeddings", which O2 misses. Yes
O4Cloud LLM Send titles to Claude, get topic labels back. API key, network, latency. Best labels. No

D1Recommendation

  1. Build the topic view on cleaned title plus URL path tokens (F1, F2). No new content permissions.
  2. Honour Chrome tab groups first (F3). Add the tabGroups permission to read group names.
  3. Classify with O1 keyword rules from config.local.js, then fall back to O2 clustering for the rest.
  4. Cache each URL's topic in chrome.storage.local so a re-render costs nothing.
  5. Keep O3 as a later upgrade behind the same classify interface. Skip O4 unless it becomes an explicit opt-in that changes the privacy story.

This fits the code as it stands. Custom groups already live in config.local.js, and the domain grouping loop in app.js is the natural place to add a second "by topic" mode.

In plain terms

Chrome already tells Tab Out the title and web address of every open tab, instantly and for free. Reading anything more from inside each page is slow, needs scary permissions, and does not work on tabs that are asleep. So the best thing to sort tabs by topic is the tab title, cleaned up, plus the words in the address.

On YouTube that title is the video name. On Gmail it is the email subject. On Google Docs it is the document name. If you already made tab groups in Chrome yourself, Tab Out should respect those first.

For the sorting itself, start with two simple tools that run inside your browser. The first is a short list of topic keywords you write in your personal config file. The second is a small word-overlap routine that groups the rest and names each group by its most common words. A smarter local AI model can be added later. Sending titles to a cloud AI would give the nicest labels, but it would break the promise that Tab Out never sends your data anywhere.

Update (27 Sep 2026): O3 is implemented as an in-browser multilingual model (paraphrase-multilingual-MiniLM-L12-v2, 118 MB, via transformers.js; extension/embeddings.js + embed-worker.js), passed to classify as ctx.embeddings and installed by scripts/setup-model.sh. Word overlap stays as the fallback. One change from the assessment: plain word overlap replaced TF-IDF weighting, because on 6 to 14 short titles the rare-word weighting pushed related pairs below accidental ones.
